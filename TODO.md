### Bugs (owner's reports, 2026-10-21)

- [x] `BUG-WALK-TO-STUTTER` — **Done 2026-10-21 (client only, live on disk, no restart).** Reproduced in a real Chromium (Visit Alderhaven from (80,25), server positions from the snapshots): the hero moved 1.4 tiles/s instead of 5.2, one tick of walking and then 100-500 ms still, at every waypoint. Cause: `routeTo` returned a waypoint on every tile, and the follower (`update()` in `field.js`) advanced only when the **drawn** hero was within .32 of it; the drawn hero eases toward the server position and trails it by about speed/14 = .37 tiles, so the server reached each waypoint (`Move` goal cleared at .12), stood idle, and waited for the sprite to catch up before the next `move` went out. Fix: (1) `pullRoute` keeps only the waypoints a straight, clear walk cannot skip (the grid cells' .55 clearance; `segmentFree` is now shared and takes a margin), so the 98-tile Alderhaven route is 11 waypoints; (2) the follower judges progress by the server position (`hero.nx/ny`) and sends the next waypoint speed x .45 s early (`routeMotion.v`, the measured speed), only when the straight line to it clears objects at .45; the last waypoint ends at .32 as before. Result: every snapshot shows the full 5.2 tiles/s, with at most an occasional one-tick hiccup from a slow frame. Check `tests/walk-route-ui.cjs` (8 checks, reads speed from the snapshots' game time; mutation-checked by serving the committed `field.js`: median 2.6 tiles/s fails). Original task: Pathing: when the player presses "walk to Alderhaven" (or any other walk-to / route destination), the character stutters forward instead of walking smoothly.
